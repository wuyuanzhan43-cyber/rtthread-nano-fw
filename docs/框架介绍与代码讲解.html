Embedded Framework v2 · 框架介绍与代码讲解

把设备模型做小，
把边界做清楚。

这是一套运行在 STM32F407VE 上的小型嵌入式框架：内核使用 RT-Thread Nano 3.1.5， 上层自建 mr 风格设备模型，板级参考 mr-library 的表驱动组织方式， 配置统一由 Kconfig 生成，CMake 与 Keil AC5 共用同一份源文件清单。

30 秒读懂

三句话说明这套框架是什么、为什么这样分层。

Kernel

RT-Thread Nano 只提供调度、IPC、时间和内核对象。没有 FinSH、ulog、设备框架，也没有默认堆；线程、事件、设备、缓冲区全部静态分配。

Device

自建设备核心保留 mr-library 的路径寻址与 open/close/read/write/ioctl/isr 语义，用一个静态注册表和四个设备类覆盖 pin、串口、SPI、显示。

Board

板级只描述“怎么接线”：stm32f407_pin_map.h 放端口/引脚/IRQ 表，Kconfig 决定启用哪些 serialN/spiN，board 只负责注册与装配。

Config

一棵 Kconfig 树生成 RT-Thread 头文件、板级头文件、框架头文件和 CMake 片段；CMake 与 Keil 消费同一个 profile，不再维护两套配置。

一条最短的调用链

应用只调用设备接口；设备类把动作翻译成驱动 ops；驱动再落到 HAL。每一层都能单独替换或测试。

阅读建议

如果你只想快速上手，先看 09 配置系统 与 10 构建系统；如果你想理解设计，按 03 → 05 → 07 的顺序阅读。

01

设计目标与边界

先把“不做什么”写清楚，框架才不会慢慢长成另一个 RT-Thread。

这套框架的目标不是“功能最多”，而是“边界清楚、可裁剪、可验证”。所有设计取舍都围绕下面这张表展开。

目标做法可检查的证据
内核只做调度/IPC/时间使用官方 Nano 3.1.5，关闭 FinSH、ulog、设备框架与堆profiles/*/generated/rtconfig.h
设备接口统一所有设备走 fw_dev_t 与六个标准动作src/framework/include/fw/dev.h
板级可裁剪逐实例 FW_USING_UARTn / FW_USING_SPInsrc/platform/stm32f407/Kconfig
无动态分配静态注册表、静态 ring、静态事件对象RT_USING_HEAP=n，map/nm 无 malloc
双工具链一致单一 project/sources.json 驱动 CMake 与 Keilcheck-manifest、gen-keil --check
逻辑可在 PC 验证Host 假设备 + CTest，不依赖 RTOS/HALsrc/tests/host/，9/9 通过

本轮明确不做

  • 不引入完整 RT-Thread：不使用 device framework、FinSH/msh、ulog、SAL；Nano 只作为调度和 IPC 内核。
  • 不 vendor 整个 mr-library：它的 ring/pin IRQ 依赖动态分配，配置也会变成第二配置源；本项目只借鉴语义和板级表结构。
  • UART DMA/EXTI：框架底座已实现，默认关闭；f407ve-dma 打开 UART1 DMA 与 pin EXTI，待上板验证。
  • 不适配 AC6：Keil 工程固定 uAC6=0、uC99=1，使用 ARMCC 5.06。
  • 不宣称硬件已验证：GCC/Keil 构建和 Host 测试已通过；真实烧录与 HIL 需要板卡，文档中明确标注边界。
边界即契约

如果你要加 FinSH、文件系统或动态设备树，建议先评估它是否值得把 Nano 换成完整 RT-Thread。当前框架的价值来自“小”，不是“全”。

02

总体架构

自上而下是使用关系，自下而上是依赖关系；framework 不认识 HAL。

应用src/app组合根 main.c：打开设备、启动串口、绘制启动画面、运行 RPC 服务
框架src/framework设备核心 + pin/serial/spi/display + 协议 + RPC 服务；不包含 HAL
驱动src/platform/stm32f407drv_pin / drv_serial / drv_spi：实现类 ops，直接操作 HAL
板级src/platform/board/stm32f407ve时钟、设备注册、console、SysTick、链接脚本
厂商src/third_party/stm32f4HAL / CMSIS / device 最小子集
内核src/vendor/rt-thread-nano官方 Nano 3.1.5：调度、IPC、timer、kservice、libcpu

目录结构

48.嵌入式框架设计2/ ├─ src/ ← 所有固件与测试源码 │ ├─ app/ 组合根 + rpc + boot + assets │ ├─ framework/ include/fw + core + components + port │ ├─ platform/stm32f407/ STM32 驱动、映射、时钟、引脚表 │ ├─ platform/board/stm32f407ve/ 板级装配、Kconfig、link.lds │ ├─ tests/ host 单测 + hil 脚本 │ ├─ third_party/stm32f4/ HAL/CMSIS/device 子集 │ └─ vendor/rt-thread-nano/ ├─ profiles/ 唯一配置源（host / f407ve / f407ve-hse） ├─ project/sources.json CMake 与 Keil 共用源文件清单 ├─ tools/ fwconfig / menuconfig / genconfig / gen_keil ├─ cmake/ 工具链与固件目标 ├─ keil/ AC5 模板、生成工程、启动文件、scatter ├─ docs/ 使用手册与本文档 ├─ Kconfig* 配置树 └─ CMakeLists.txt

依赖红线

  • src/framework/core 与 components 不包含 HAL / RT-Thread 头文件；RTOS 相关能力通过函数指针注入（lock/unlock、wait_rx、fw_clock_t、fw_delay_ms），只有 port/rtthread 例外。
  • src/platform/stm32f407 只实现设备类 ops；它认识 HAL，但不决定“哪个 UART 是控制台”。
  • src/platform/board 只做时钟、引脚编号、实例注册；它不实现 class 语义，也不绘制启动画面。
  • src/app 是唯一业务层：命令、上报、启动画面和图片都在这里；它只使用 fw_dev_* 与 class helper，不直接访问寄存器。
为什么把 src/ 收成一个大目录

根目录只保留配置、构建、文档和工具；阅读代码时只需要打开 src/。第三方与自研代码仍在同一棵树内，但通过 third_party/、vendor/ 明确区分，避免误改上游。

03

设备核心：路径、ops 与引用计数

整个框架只有一份设备表；所有类都通过同一组动作被调用。

fw_dev_t 是“基类”，必须放在具体设备结构体的第一个成员。注册表只保存基类指针，具体类通过 FW_CONTAINER_OF 从基类地址反推外层对象。

三个基础结构

两层 ops 的意义

dev->ops 是“设备类”实现，由 fw_dev_* 分发；drv->ops 是“具体芯片驱动”实现，由类在调用前强制转换成对应的 ops 类型。类只认识语义，不认识寄存器。

注册：线性扫描的静态表

设备数量在十几个量级，线性查找比哈希表更简单，也不需要动态内存。名字会先归一化："serial1" 与 /dev/serial1" 指向同一个设备。

打开：只在 0 → 1 时调用类的 open

引用计数让“多个模块共享同一个控制台”变得安全：最后一次 close 才会真正清空缓冲。当前 pin 类没有 open/close，spi 类只保存配置，serial 类在第一次 open 时清空 ring 并重新配置波特率。

container_of：从基类找回外层对象

fw_serial_t ← 实际静态对象 ├─ fw_dev_t dev ← 注册进设备表的是这个成员的地址 │ ├─ name[16] │ ├─ type / ref_count │ └─ ops / drv ├─ fw_serial_config_t config ├─ fw_ring_t rd_fifo ├─ fw_ring_t wr_fifo └─ volatile fw_status_t error FW_CONTAINER_OF(dev, fw_serial_t, dev) = (fw_serial_t *)((char *)dev - offsetof(fw_serial_t, dev))
布局约束

具体设备的 fw_dev_t 必须是第一个成员。这不是风格问题，而是 FW_CONTAINER_OF 与设备表类型擦除的前提；新增设备类时必须遵守。

04

pin：一个设备覆盖所有 GPIO

不为每个引脚创建对象，用编号表达“端口 + 引脚”。

STM32F407VE 有 5 个端口、80 个引脚。如果每个引脚一个设备，设备表很快被占满，注册代码也会变得冗长。pin 类采用 mr-library 的编号方式：一个 "pin" 设备 + offset。

编号编码

驱动用位运算拆出端口下标和引脚掩码，再查 stm32f407_pin_map.h 的两张表；引脚号本身不依赖 HAL 的寄存器布局。

应用侧用法

ISR 安全

read 只读 IDR，write 使用 BSRR，都是原子寄存器操作，不涉及“读-改-写”，因此可以在中断里调用。

configure 的边界

configure 会调用 HAL_GPIO_Init 并可能改写整个引脚配置，只允许在任务上下文、初始化阶段调用。

stm32f407_pin_map.h 的角色

DRV_PIN_PORT_CONFIG、DRV_PIN_CONFIG、DRV_PIN_IRQ_MAP_CONFIG 是编译期表。板级移植时改这张头文件即可；驱动不关心具体是 A..E 还是 A..I。

05

serial：ring、事件与中断

任务只碰 ring，ISR 只搬字节；两者通过驱动注入的临界区串行化。

每个启用的 UART 对应一个 serialN 设备。类层保存配置和两个 ring，驱动保存 HAL 句柄、USART 指针、事件对象和静态存储。这样 ring 容量由 Kconfig 决定，而类层保持芯片无关。

对象布局

drv_serial_t ← 驱动静态实例 ├─ fw_serial_t base │ ├─ fw_dev_t dev ← 注册进设备表 │ ├─ fw_serial_config_t config │ ├─ fw_ring_t rd_fifo → 指向 rx_storage │ └─ fw_ring_t wr_fifo → 指向 tx_storage ├─ UART_HandleTypeDef hal ├─ USART_TypeDef *instance ├─ IRQn_Type irq ├─ struct rt_event rx_event ├─ volatile bool started / tx_active ├─ uint8_t rx_storage[FW_SERIAL_RX_BUFSZ] ├─ uint8_t tx_storage[FW_SERIAL_TX_BUFSZ] └─ fw_drv_t drv

驱动 ops：类只认识语义

ops由谁调用职责
configure类 open / SET_CONFIG把波特率、位宽、停止位、校验位写入 HAL 并重新初始化
read_byte类的 RD ISR 分支读取 DR，返回 0..255
write_byte类的 WR ISR 分支把一个字节写入 DR
start_tx类 write 成功入队后按需打开 TXE 中断
stop_txWR 分支发现 ring 空关闭 TXE，结束发送
wait_rx类 read / wait_rx等待 RT 事件，超时返回 FW_ETIMEOUT
lock/unlock类访问 ring 时关/开中断，保护任务与 ISR 共享的索引

RX 路径

1
USART RXNE 置位硬件收到一个字节，进入 USARTx_IRQHandler。
2
驱动调用 fw_dev_isr(RD)类通过 read_byte 读走 DR，并把字节写入 rd_fifo。
3
rt_event_send 唤醒等待者等待在 wait_rx 上的任务变为就绪；真正切换发生在中断退出时。
4
任务从 ring 拷贝数据serial_read 在临界区内批量读走可用字节，返回实际数量。
为什么先检查再等待

ISR 可能恰好发生在“类发现 ring 为空”和“进入事件等待”之间。类的第一次检查 + 驱动 wait_rx 内部的再次检查形成双重检查，消除丢失唤醒的窗口。

中断处理体

TX 路径：非阻塞短写

fw_dev_write 只把数据放进 TX ring，然后按需打开 TXE 中断。实际逐字节发送由 ISR 完成；ring 空时 ISR 关闭 TXE。

返回值语义

write 返回“已进入 ring 的字节数”。短写不是错误，而是背压；app_rpc 用 tx_offset 记录进度，下一轮继续发送剩余部分。

错误语义

RX ring 满时 serial_isr 记录 FW_EOVERFLOW；下一次 read 会先上报错误并清空 RX ring，避免应用继续消费不完整的数据。

临界区注入：core 不依赖 RTOS

类层只调用函数指针，不包含 rtthread.h。同一套 serial 类可以换到裸机临界区、其他 RTOS，甚至 Host 假设备（lock 返回 0）。

控制台的双模式

rt_kprintf 启动早期没有中断和调度器，只能轮询 USART 寄存器；串口 start 之后改为把字符串放进 TX ring，非阻塞返回。

日志也会丢

运行期控制台走非阻塞短写；如果 TX ring 满，多余的日志字符会被丢弃。这是为了避免 rt_kprintf 在高频日志时阻塞业务。需要可靠输出时，应使用协议回复而不是日志。

06

SPI 与显示：把面板当设备

SPI 负责总线，display 负责窗口/像素/背光，ST7735S 只实现面板时序。

SPI 类

SPI 是同步总线，没有 ring 和中断事件。类层保存配置并转发同步传输；驱动用 HAL 的 Transmit / Receive / TransmitReceive 完成一次事务。片选由具体外设通过 pin 设备控制，SPI 类不涉及。

display 类

display 是本项目扩展的类：固定 RGB565，提供初始化、窗口写入、像素流、结束写入和背光五个面板 ops。通用裁剪与分块放在类层，面板驱动只关心命令序列。

面板 ops典型实现（ST7735S）
init硬件复位 + 初始化命令表 + 清屏 + 开背光
begin_writeCASET/RASET 设置窗口，发 RAMWR，DC 切到数据模式
write_pixelsRGB565 拆成大端字节，按 32 像素一块发送
end_write释放 CS，结束写事务
set_backlight按有效电平写 BL 引脚
为什么是 16 像素一块

最大矩形是 128×160，如果一次性构造整屏需要 40KB 缓冲。分块后栈上只需要 32 字节，既避免大栈，也避免长时间占用 SPI。

ST7735S 如何组合设备

st7735s_t ├─ fw_display_t base ← 注册为 "lcd" ├─ fw_dev_t *spi → "spi1"（或 spi2/spi3） ├─ fw_dev_t *pin → "pin" ├─ int cs / dc / res / bl ← FW_PIN_NUMBER 编码 ├─ uint16_t x_offset / y_offset ├─ uint8_t madctl └─ bool ready / writing 一次窗口写入： pin(CS=0) → pin(DC=0) → spi(命令) → pin(DC=1) → spi(像素流) → pin(CS=1)

面板驱动不直接操作 HAL；它通过 fw_spi_transfer 和 fw_pin_write 工作，因此可以在 Host 上用假设备验证裁剪/分块逻辑。

启动画面

app_boot_display()（位于 src/app/boot/app_boot.c）先调用 fw_display_setup() 执行面板初始化，再按 APP_BOOT_MODE 选择四色横条、头像图片或纯白诊断。头像是一张 128×160 RGB565 常量表，占 40KB Flash；选择其他模式时可由链接器回收。

06b

任务管理与健康度

main 监督，rpc 工作；栈、CPU、状态和心跳都可在运行时查询。

线程模型

main 只做设备/任务初始化，然后进入监督循环；app_rpc 是独立的静态任务， 独占串口并每轮调用 fw_task_heartbeat_self()；idle 只参与 CPU idle 统计。 RPC 任务等待上限为 500ms，避免心跳饥饿。

健康度

框架用静态任务表记录每个任务；port 通过扫描 RT-Thread 预填的 '#' 估算栈高水位， SysTick 在 rt_tick_increase 前按当前/idle/other 归桶计算 CPU。 健康等级为 OK/WARN/LOST，异常原因包括栈低、心跳 warn、心跳 lost 和线程关闭。

指标来源判定
栈port 快照 + '#' 扫描剩余 < 阈值 → WARN
CPUSysTick tick 桶窗口内每任务/总占用千分比
状态rt_thread->statINIT/READY/RUNNING/SUSPENDED/CLOSED
心跳fw_task_heartbeat_selfwarn 1.5s / lost 3s

挂起与恢复

RT-Thread 的 rt_thread_suspend() 只接受 READY 线程，因此 suspend 只置 suspend_pending，目标任务在下一次 heartbeat 时自行挂起；resume 只接受 user_suspended 的任务。main 不可控，异常不自动重启。

运行时查看

0x05 返回总数、ok/warn/lost、worst/current 索引和 busy/idle/other； 0x06 按索引返回状态、栈、CPU、心跳；0x07 执行 suspend/resume/set_priority。单帧 payload 上限 32 字节，详情固定 31 字节。

07

BSP 与 board：谁负责接线，谁负责语义

board 只说“哪个引脚接了什么”，bsp 只说“怎么操作 STM32”。

stm32f407_pin_map.h：编译期引脚表

这就是参考 mr-library 的地方：板级用宏表描述端口、引脚和 IRQ，驱动只做下标查表，不写一堆 switch。当前 pin 类还没有实现外部中断，IRQ 表预留给后续扩展。

逐实例生成：Kconfig 直接决定注册代码

引脚和 AF 全部来自 board_config.h，所以“启用 UART2”不需要改 C 代码：在 menuconfig 中打开 FW_USING_UART2，再调好 BOARD_UART2_* 即可。

注册顺序

1
drv_pin_register()唯一的 pin 设备；后续 LED 和 LCD 控制引脚都依赖它。
2
LED 引脚配置按 Kconfig 设置输出模式和“灭”的初始电平。
3
drv_serial_register_all()注册 serial1..N；此时中断还未打开。
4
drv_spi_register_all()注册 spi1..N，完成 GPIO 复用和 HAL 初始化。
5
LCD 注册配置 CS/DC/RES/BL，注册 "lcd"；真正的面板初始化留到 main。

职责边界

层知道什么不知道什么
app设备名、协议、业务策略USART/GPIO 寄存器、引脚复用
framework设备语义、ring、协议帧、显示裁剪HAL、RTOS、板级引脚
bspSTM32 外设、HAL、中断、引脚表哪个 UART 是控制台、LED 的板级含义
board板级接线、时钟、实例选择、启动顺序设备类内部缓冲区/协议语义
只改 Kconfig 的验收场景

启用 UART2 + SPI2、把 UART2 映射到 PD5/PD6、LED 改到 PE3，不修改任何 C/H；CMake 与 Keil 都能构建，产物中可见 serial2、spi2、USART2_IRQHandler。

08

启动流程：从复位到 main

设备在调度器启动前注册，中断在 main 打开串口后才启用。

1
Reset_Handler启动文件从 Flash 读取初始 MSP 和复位向量，初始化 .data/.bss。
2
SystemInit启动文件内的基础时钟设置；随后进入 RT-Thread 的 entry。
3
rtthread_startup初始化内核对象、调度器、timer，然后调用 rt_hw_board_init()。
4
rt_hw_board_initstm32f407_boot_init(board_clock_config())：HAL/时钟/SysTick/heap/复位原因；然后 board_devices_init()。
5
board_devices_init先 board_pins_validate()，再注册 pin / serial / spi / lcd 并绑定控制台；UART 中断仍未打开。
6
mainopen 控制台 serial → board_serial_start_all() → LCD 初始化 → app_tasks_init/start → 健康监督循环；RPC 在独立 rpc 任务中运行。

一个 SysTick，两套时间

HAL 与 RT-Thread 都想要 SysTick。这里统一由 rt_hw_systick_init() 按 RT_TICK_PER_SECOND 配置重装载值，SysTick_Handler 同时调用 HAL_IncTick() 和 rt_tick_increase()。

HAL_IncTick 按 systick_ms = 1000 / RT_TICK_PER_SECOND 累加，保证 uwTick 始终以毫秒为单位；即使把 tick 改成 100Hz，HAL 时间也不会变成 10ms 粒度。

延时钩子

stm32f407_delay_ms 被安装为 fw_delay_ms 的实现：调度器已启动且不在中断中时使用 rt_thread_mdelay，否则用 SysTick 忙等。这样 ST7735S 驱动可以调用 fw_delay_ms，而 framework 不需要包含 rtthread.h。

失败就停机

时钟或设备注册失败会调用 stm32f407_panic：关中断、保存文件名/行号、原地空转。启动阶段还没有可用的控制台，保留现场给调试器是唯一可靠的诊断方式。

生成阶段的校验

协议与RPC 服务

逐字节状态机 + 非阻塞 TX 泵，演示完整的设备层使用方式。

帧格式

+------+------+-----+-----+-----+---------+--------+--------+ | A5 | 5A | LEN | SEQ | CMD | PAYLOAD | CRC_LO | CRC_HI | +------+------+-----+-----+-----+---------+--------+--------+ LEN 0..32 SEQ 回复沿用请求值 CMD bit7=0 请求；bit7=1 回复/事件 CRC CRC-16/CCITT-FALSE，覆盖 LEN..PAYLOAD
命令方向请求回复
0x01 PING请求/回复空00 "PONG"
0x02 LED_SET请求/回复1 字节 0/100
0x03 STATUS请求/回复空00 known state
0x04 STATS请求/回复空00 frames io_errors partial_timeouts report_seq
0x05 TASK_SUMMARY请求/回复空00 total ok warn lost worst current busy idle other
0x06 TASK_DETAIL请求/回复index00 state health reasons priority name stack cpu heartbeat
0x07 TASK_CONTROL请求/回复index/action/valuestatus
0x90 STATUS主动上报—00 known state

解析状态机

解析器每个字节只做一次状态判断，不需要先攒够整帧；非法长度或 CRC 错误只计数并重新寻找前导码，不会卡死。若错误字节本身是 0xA5，会把它当作下一帧前导码继续，避免漏掉紧邻的合法帧。

RPC 任务循环

app_rpc_next_wait_ms 返回未发完的 TX、周期上报和半帧超时的最小值； RPC 任务再把它 clamp 到 500ms，保证心跳年龄远小于 warn 阈值。main 不再处理 RPC， 只负责初始化、创建任务和周期调用 fw_task_refresh。

单轮 RX 预算

一次 poll 最多消费 rx_budget 字节（默认 64），避免持续有数据时主循环饿死上报和超时检查。这不是吞吐瓶颈：串口 ring 已经吸收了突发数据。

HIL 脚本

src/tests/hil/test_protocol.py 通过 USB-UART 与真实板卡交互，覆盖主动上报、PING、LED/STATUS、未知命令、非法参数、噪声恢复、分片帧、可选 STATS，以及 --tasks 时的任务摘要/详情/self-suspend 拒绝。

取舍与扩展

每个“没有做”的功能都有明确原因；扩展点也保持在同一条边界上。

关键取舍

问题选择代价 / 收益
是否 vendor 整个 mr-library否，自建静态 mr 语义 core少了动态设备树/读写锁；换来无 malloc、RAM 可预测
设备查找固定数组 + 线性扫描O(n) 查找；n≤16，简单且无分配
串口 TXring + TXE 中断 + 短写非阻塞；调用者需要处理短写和重试
RTOS 解耦lock/unlock、wait_rx、clock、delay 全部注入多一层函数指针；core 可在 Host 测试
配置Kconfig + 生成头文件需要运行生成器；换来单一配置源和 menuconfig
Keil 工程模板 + 生成，不手工维护不能在 GUI 里永久改选项；换来与 CMake 一致
UART DMA/EXTI框架已实现，默认关闭f407ve-dma 打开；时序需上板验证

新增一个设备类

  1. 在 src/framework/include/fw/ 定义类型令牌、ops、设备结构体和公开 API；
  2. 在 src/framework/core/ 实现类包装：只做参数校验、状态保存和 ops 转发，不包含 HAL；
  3. 在 src/platform/stm32f407/ 实现具体芯片 ops；
  4. 在 src/platform/board/ 或设备自己的注册函数中创建静态实例并注册；
  5. 把新源文件加入 project/sources.json，运行 check-manifest 与 gen-keil；
  6. 在 src/tests/host/ 加一个假设备，覆盖 open/read/write/ioctl 和错误路径。
扩展红线

类层不包含 HAL/RT-Thread；驱动不决定设备名和板级策略；board 不实现类语义。只要守住这三条，新增设备不会破坏现有分层。

只改 Kconfig 增加一个串口

  1. menuconfig 打开 FW_USING_UART2；
  2. 确认 BOARD_UART2_TX/RX_PORT/PIN/AF；
  3. 运行 python tools/fwconfig.py sync --profile f407ve；
  4. 重新生成 Keil 工程并构建。

不需要修改 drv_serial.c、board_devices.c 或 CMake/Keil 工程文件：实例、ring、中断函数都由 Kconfig 和生成的头文件决定。

注释策略

源码采用中文注释，文件头写明层级/职责/上下文/依赖；公共 API 说明参数、返回值和调用上下文；关键路径解释“为什么”而不是“做了什么”。自研 C/H 的注释密度约 40%，外部 vendor/third_party 保持上游风格，不做大面积改写。
